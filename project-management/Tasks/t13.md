## Problem Statement

The game does not run.

A player who opens the demo gets an empty canvas. The repository contains a complete, tested foundation — a scene host, a typed event bus, one seeded random source with deterministic forks, input intents with keyboard and gamepad parity, and pure rules for affinity, turn order, and the presence ladder — and **none of it is ever constructed.** What renders is a renderer, a scene, and a camera with nothing in them.

This is a problem for the player because there is no game. It is a problem for the design owner because nothing about the direction can be judged until it is visible. And it is a problem for every other Scene 1 ticket because the two diagnostic surfaces the project's evidence rules depend on do not exist on a live page, so no browser evidence can be gathered at all and no scene work can begin.

The foundation is done and proven. The seam between it and a running game is the only thing missing, and until that seam exists everything downstream is blocked.

## Solution

A player opening the page gets a running scene they can interact with, and the project gets the two diagnostic surfaces it depends on.

Concretely: the game boots, runs its loop, accepts input, and reports its own state. The first state it passes through is the **ghost terminal** — the boot state the scene contract names first. A player can reach that state, the state reports what it applied, and the two `window` surfaces the evidence pass reads are present and populated on a live page.

The intro that follows the boot is **not** in this spec. This spec ends the moment the game is running, reachable, observable, and instrumented. Everything the player then sees is the next ticket's problem.

## User Stories

**The player**

1. As a player, I want the page to show me a running game rather than an empty canvas, so that I know the demo works at all.
2. As a player, I want the scene to draw something from the first frame, so that I am not looking at a blank screen wondering whether it is broken.
3. As a player, I want the game to respond to my keyboard without a "click to start" step, so that nothing stands between me and the scene.
4. As a player, I want the game to respond to a gamepad the same way it responds to a keyboard, so that my choice of input does not change what the game does.
5. As a player, I want my first keypress to silently satisfy the browser's audio requirement, so that sound works later without me having to unlock it explicitly.
6. As a player, I want the game to keep running at a steady pace regardless of my machine's frame rate, so that the scene I see does not depend on my hardware.
7. As a player, I want the game to keep running after I switch away from the tab and come back, so that it does not die while I am not looking.
8. As a player, I want the game to reach the ghost terminal state on boot, so that I am in the scene the demo is named for.
9. As a player, I want the page to be legible rather than blank if the game fails to boot, so that I am not left guessing whether it is broken or still loading.
10. As a player, I want to be told the game loaded, rather than left to infer it, so that I know I have arrived.

**The agent building the scene**

11. As an agent building the scene, I want a host I can construct and start in one place, so that I do not need to know how the foundation works internally.
12. As an agent building the scene, I want a single place that owns the renderer, the scene, and the camera, so that I am not competing with another ticket for them.
13. As an agent building the scene, I want to hand the boot the same seeded random source the rules use, so that my scene is reproducible from a seed.
14. As an agent building the scene, I want to ask the game to move to a named state and be told what it did, so that I can drive the scene without reading the host's internals.
15. As an agent building the scene, I want a request for an unknown state to be refused rather than silently ignored, so that my mistakes surface immediately instead of producing a scene that quietly does nothing.
16. As an agent building the scene, I want the game to expose what it is currently doing, so that I can check my work without guessing.
17. As an agent building the scene, I want the boot to be one file's responsibility, so that I know exactly what I own and what I must not touch.

**The evidence pass**

18. As the agent gathering browser evidence, I want both diagnostic surfaces to exist on a live page, so that I can read real numbers rather than infer them from source.
19. As the agent gathering browser evidence, I want the diagnostics to report real rendering activity, so that I can prove the canvas is actually drawing and not merely present.
20. As the agent gathering browser evidence, I want to drive the game to the ghost terminal state from the automation, so that I can prove the state is reachable through the real path rather than only in a unit test.
21. As the agent gathering browser evidence, I want a boot that fails to produce a usable message, so that a red run tells me what broke.

**The reviewer and the design owner**

22. As the reviewer, I want the boot to change nothing about how the rules behave, so that I can review a wiring change rather than a behaviour change.
23. As the reviewer, I want the accessibility settings the player uses to be the same ones the boot reads, so that a code path cannot quietly bypass what the player chose.
24. As the design owner, I want the game running so that I can finally judge the direction against something real rather than a description.
25. As the design owner, I want the boot to make none of my four open presentation decisions for me, so that the first thing I see is not a choice I did not make.

## Implementation Decisions

- **A single boot entry owns the renderer, the scene, the camera, and the host.** That entry is the only file in this ticket's boundary. Nothing it does may be duplicated elsewhere, and no other ticket may create a renderer.
- **The host is constructed, not modified.** The foundation already provides the host and the state machinery. This ticket wires them together; it does not extend them. Needing to change the foundation means the ticket is wrong, not the foundation.
- **The state contract is already satisfied.** The scene contract names thirteen states in order, and the boot state is the first. The foundation already declares it. No registration is required by this ticket — reaching it is.
- **State transitions go through the host.** The boot must not set a state by writing a variable. It requests the transition and the host decides. Unknown state names are refused with a message that names the refused state.
- **One seeded random source, shared.** The boot constructs from the seeded source rather than the platform random, so the same seed produces the same scene.
- **Input intents are the only input surface.** The boot subscribes to intents; it does not read key events directly. Keyboard and gamepad must flow through the same path so parity is structural rather than maintained by hand.
- **The loop is the foundation's, not the boot's.** The boot starts it and does not implement a second animation path.
- **Diagnostics are exposed as two distinct `window` surfaces**: one for the test hooks an automated pass drives, and one for readable diagnostics. Both must be present and populated on a live page. Their names are fixed by the evidence pass and are not this ticket's choice.
- **Accessibility preferences are read, never inferred.** Reduced motion and debug-hide must drive the same settings object the rest of the game reads, so that a preference set once applies everywhere.
- **The failure path is visible.** A boot that throws must leave the player a legible message rather than a blank page.
- **No new dependency is required.** Everything needed already exists in the foundation, the renderer, and the test tooling.

## Testing Decisions

**What makes a good test here.** Only external behaviour. A test may assert that the host was constructed and started, that a transition reported the state it applied, that an unknown state was refused, and that the diagnostic surfaces exist and carry real values. A test may **not** assert the shape of internal private state, the order of private calls, or anything that would pass unchanged if the game stopped drawing. The distinction that matters: a test that would still pass with the canvas switched off is not a boot test.

**Modules tested.** The boot entry itself, through its public seam. The foundation is already covered by the existing suite and must not be re-tested here.

**Prior art.** The suite already tests pure rules as external behaviour, and the pure-rule tests were written before their implementation. Follow that: write the failing test first, run it, observe it fail, then implement. The browser pass already has a boot spec; extend it rather than starting a second one.

**Two levels, both required.**

- A **unit-level test** that runs with no browser and asserts the wiring: the host is constructed, started, driven to the boot state, and both diagnostic surfaces are assigned. This must fail before the implementation exists.
- A **browser-level test** that runs the real page and asserts the canvas is genuinely drawing — non-zero dimensions, a live context, and diagnostics showing real rendering activity — plus that the boot state is reachable by driving the automation, not by reading source.

**What must be reported.** The real output of the type check, the unit suite, and the production build, and the real output of the browser pass. If the browser pass cannot run in the agent's environment, that must be stated plainly and the affected criteria marked unverified. A claim without output is not evidence.

## Further Notes

**Four decisions deliberately left open.** This ticket is independent of all four. If the agent cannot proceed without answering one, it stops and reports the question. An invented answer will be reverted.

1. **Console presentation** — composed text over the canvas, a texture on a mesh, or a hybrid. The spec names one; the owner's direction describes a console that genuinely becomes a three-dimensional object. Unresolved.
2. **First-frame colour** — the current near-black-with-a-green-cast house colour is used in two places and appears deliberate, but the owner's direction says the system starts black. Unresolved.
3. **Boot text visibility** — the existing status line is visible, contradicts "no border, no frame, nothing", and is also the polite live region assistive technology reads. The boot entry does not own that file. **Report it; do not fix it.**
4. **Audio unlock** — browsers require a gesture. The recommendation on the table is no "click to start", with the first keypress unlocking silently. Unresolved.

**A verified trap, recorded so the agent does not have to rediscover it.** The boot state this ticket must reach is **already declared by the foundation**. A previous attempt assumed it had to be registered and nearly reached outside its boundary to do it. It does not. Construct the host and request the transition.

**Why this ticket is one file.** It is the seam between a finished foundation and everything downstream. It touches the widest surface and changes the least behaviour, which is exactly why it is a single-file ticket with a hard boundary. It is also the ticket whose failure is most visible and whose success unblocks the most.
