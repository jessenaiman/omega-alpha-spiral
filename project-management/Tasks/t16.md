## Why this ticket exists

The design owner wants to change how the game actually plays. The current Scene 1 logic was built against a suite of tests the owner did not fully author, and several of the behaviours those tests assert are now considered **bad logic** that will change. When the change lands, the suite will fail — by design. That is a *signal to update the tests*, not a signal to stop.

**The wall, named and counted.** `tests/unit/` holds **51 tests** that lock the current logic:

| File | Count | What it locks |
|---|---|---|
| `tests/unit/scene-one.test.ts` | 16 | affinity ids and scoring (`light` / `shadow` / `ambition`, +1 / +2 / +1 rules), leader + tie-break, the ladder rungs, the Dreamweaver turn sequence |
| `tests/unit/scene-one-run.test.ts` | 9 | a whole canonical run walk: question rotation, rungs, closing question, refusing unaccepted actions |
| `tests/unit/core-runtime.test.ts` | 25 | the deterministic foundation: seeded RNG reproducibility, shuffle, the no-`Math.random` guard, event bus, fixed loop, keyboard/gamepad intents, settings, diagnostics, state registry |
| `tests/unit/bot-playtest.test.ts` | 1 | ghost / reckless-driver bot-playtest metrics |

The scene-one pair asserts the creative decisions — the ones the owner is most likely to overturn (and note [[t15]]: some of the asserted values, starting with the trio itself, are already disputed canon on this machine). The core-runtime pair asserts the deterministic scaffold — most of it is durable infrastructure worth keeping, but it still blocks refactors while it names current module shapes and behaviours.

## The rule

- **Legacy tests are not canon.** They encode decisions *as played at the time of writing* (marked "fixed by the design owner" in a comment in `scene-one.test.ts`). A later owner ruling overrides an earlier one; the ticket that carries the ruling is the authority, not the test line.
- **A test failure on an intended change is the expected wall.** The change ships with its tests updated: old assertions that encoded the previous decision are replaced with assertions that encode the new agreed behaviour, and the whole updated suite runs green as part of **Verify**.
- **Never break the deterministic contract without saying so.** The seeded-RNG and no-`Math.random` guarantees are the game's reproducibility contract. Changing them is itself a ruling — flag it, don't bury it.
- **Where the disputed canon is involved, get the ruling first.** Several asserted values depend on the [[t15]] trio decision. Do not let an agent "fix" the tests to whichever trio it prefers; the owner rules, then the tests follow.

## Acceptance

- The ticket is cited, by the owner or an agent, at the first moment a legacy test blocks an intended change.
- Any committed change that was born as "the tests won't let me" includes the updated tests inline in the same commit, plus evidence the full suite runs green.
- No refusal is accepted on the grounds "the tests assert the old behaviour" without this ticket being named and the disputed assertion linked to its owning decision/[[t15]].

## Verify

- `grep -c "^test(" tests/unit/*.test.ts` before and after a logic change, with a comment on the delta in the change's commit/PR.
- `npm run test:unit` green after the change, and the diff of the updated test files shown as evidence.

## Output

- Each time the wall is hit and handled, a note appended here: which change, which tests were updated, and which owner ruling (or ticket) authorized it. This becomes the ledger of test-authority changes.
